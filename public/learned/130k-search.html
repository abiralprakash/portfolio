Making 130,000 trademark records searchable

Search · D1 · Production desks

Search in NepalIPMS is not a convenience feature. Paralegals run it while clients are on the phone: “Does this mark conflict?” “What happened to application 12345?” “Show me everything in class 35 for this company.” If the query takes three seconds, the conversation stalls and trust erodes. Our target was sub-200ms for typical lookups on a register of more than 130,000 rows — on infrastructure we could operate from Kathmandu without a dedicated search cluster.

The first mistake would have been treating the register like a generic full-text problem. Trademark data is messy: mixed Nepali and English marks, punctuation that means something legally, application numbers that users type with and without slashes, and class filters that must combine cleanly with free text. We normalized aggressively at ingest — folding case, stripping decorative characters where safe, keeping canonical application number forms — so queries hit predictable tokens.

D1’s FTS5 extension became the backbone, backed by composite filters for status, class, and owner where indexes mattered. We avoided over-fetching: paginated results with the fields the list view needs, detail fetched on selection. Hot queries — common marks, repeated client portfolios — got a short TTL cache in KV so the edge did not hammer the database on every keystroke in a busy morning.

Performance work showed up in UX, not benchmarks alone. Debounced input, instant empty states, and clear “no match” messaging kept the interface calm when lawyers typed partial marks. We logged slow queries in production and tuned indexes based on what desks actually searched, not what we guessed in design.

Scale is relative. One hundred thirty thousand rows is not big data — but it is big enough that naive LIKE scans fail, and small enough that a well-indexed SQLite at the edge can win. The lesson: match the architecture to the latency budget of the human waiting on the other end of the phone.
