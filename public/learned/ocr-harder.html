Things I've learned

OCR is harder than the demo suggests

Document intelligence · Bulletin intake

A crisp photo of a printed page fed into a cloud OCR API returns impressive text in a conference slide. Department of Industry trademark bulletins are not conference slides. They are multi-column PDFs, scanned at uneven quality, mixing Devanagari and Latin scripts, with table rows that break across pages and application numbers that must land in the correct matter field — not merely somewhere in a text blob.

We wired Azure Document Intelligence into NepalIPMS because layout-aware extraction beat raw character dumps on the first real bulletin. Even then, the pipeline needed a parse layer: map bounding regions to semantic fields, detect when a row continues from the previous page, and flag rows where confidence scores drop below what we would merge automatically. OCR output is a proposal, not a fact.

The product decision that saved us was human review by default. Extracted rows land in a queue where a paralegal sees the source PDF beside structured fields. One keystroke to confirm, two to fix a class digit, reject if the scan is unusable. Over time we learned which bulletin layouts fail and tuned pre-processing — deskew, contrast — before sending pages upstream.

Bilingual text added another layer. Marks may appear in Nepali while legal metadata stays in English. Tokenizers and search indexes on the other side of the pipeline need the same normalization assumptions as the OCR mapping, or you will extract correctly and still fail to find the record later.

Demo culture undersells operational OCR. The hard work is idempotent workers, storage of raw pages in R2 for audit, retry when vendors throttle, and never silently corrupting a live register. The lesson I keep repeating: treat document intelligence as a workflow product, not a model API with a checkbox.
